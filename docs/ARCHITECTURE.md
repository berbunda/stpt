# STPT Architecture

Protocol specification: https://github.com/berbunda/stpt-protocol/blob/main/specs/PROTOCOL.md

Protocol work status (2026-11-22, specification draft-49): PE001–PE005 define draft file transfer profile 1. RE001 implements the Channel envelope; RE002 implements explicit `stpt fs` commands, POSIX Server operations and ordinary verified transfers. Base path encoding and mandatory kind/size metadata are prerequisites of these operations. RE003 implements explicit verified resume of uploads and downloads. RE004 implements lossless path/entry validation, Windows drive encoding/Client responses and informational metadata on available platforms. RC008 implements the Windows terminal Server with ConPTY and its current process Account/token; 0.4.1-0 adds the native Windows file service for that same Account/token and resolves G3 (§17). Tier RE scenario review is complete in 0.4.1-2 (§18). File implementation: §12–§15 and §17.

Tier PE received a specification scenario review on 2026-11-21; results are in [PE_REVIEW.md](https://github.com/berbunda/stpt-protocol/blob/main/docs/PE_REVIEW.md). Draft-41 clarifies rename fields, directory listings, integrity-error precedence, progress deadlines and retained upload parent identity. This is documentation review, not runtime validation; subsequent implementation validation is described in §12–§15.

# 2	Command line
- One binary, one explicit subcommand per operation: `server`, `connect`, `exec`, `sessions`, `detach`, `terminate`, `trust list`, `trust remove`.
- `server` accepts Connections (§6); `server --fingerprint` prints the fingerprint of the Server key and exits (§7). The Client commands with a destination load the user key, establish a Connection, verify the Server key (§7), exchange HELLO (§8) and authenticate (§9). `connect` and `exec` then run a terminal Channel (§10), `sessions`, `terminate` and `detach` send requests (§11); the Connection is closed regularly afterwards. `trust` manages the trust store.
- The destination, `--fingerprint SHA256:...` and `-i/--identity PATH` (user key) form `cli::Remote`, flattened into every Client command with a destination.
- Destination `account@host[:port]`: the last `@` separates the Account (so `user@domain` Accounts work), IPv6 addresses go in brackets, the default port is 843, the Account name is at most 256 bytes (PROTOCOL.md §13.4).
- Server address (`destination::Address`, also `trust remove HOST[:PORT]`): normalized at parsing, so equal addresses compare equal: DNS names in lower case, IP addresses in canonical form (`[0::1]` = `[::1]`). A host with a space, control character or bracket is refused, so it cannot break a trust store line.
- Session arguments are kept as text and resolved through the Session list (§11): full ID, then name, then unique ID prefix (case-insensitive).
- Exit codes: 0 success; 2 command line error (clap); 255 STPT or Connection error. `exec` will return the remote exit code.
- Global options `--config`, `-v`/`--verbose` (repeatable), `-q`/`--quiet` are accepted before or after the subcommand. clap does not detect a conflict of global options given on different levels (`-q server -v`), so `Cli::validate` checks `-q` with `-v` after parsing.

# 3	Roles
- The same binary is Client and Server; the subcommand selects the role. `cli::Command` has the variant `Server` and the flattened `Client(ClientCommand)`, so the dispatch in `cli::run` is by role and each role module receives only its own commands.
- Client and Server share only common modules (now `destination`, `identity`, `quic`, `tls`); a role module does not use the other role.
- The command line is the same on every platform. Unix PTY and Windows ConPTY provide Server mode; G2 is resolved. Windows serves its current Account/token for terminals (§16) and local-volume files (§17); G3 is resolved.
- Default listen address `[::]:843`, dual-stack (§6).

# 4	Configuration
- TOML, one file per role, read once at start. `--config PATH` (global option, before or after the subcommand) replaces the default file.
- Default files: Server `/etc/stpt/server.toml` on Unix or `%PROGRAMDATA%\stpt\server.toml` on Windows; Client `$XDG_CONFIG_HOME/stpt/config.toml`, else `~/.config/stpt/config.toml` (a relative `XDG_CONFIG_HOME` is ignored, as the XDG specification requires), on Windows `%APPDATA%\stpt\config.toml`.
- A missing default file means built-in defaults; a missing `--config` file, any other read error, a syntax error, a wrong value or an unknown key ends the program with 255 and `stpt: config: PATH: reason` (`deny_unknown_fields`: a misspelt key never falls back to a default silently).
- Precedence: command line, then file, then built-in default.
- Client keys: `detach_timeout` (§11), sent when `connect` or `exec` creates a Session, never on attach; `reattach_timeout` (§11). A key is added with the item that uses it. The Client configuration directory also holds the trust store `known_servers` (§7); `config::client_dir` gives the directory.
- The Server checks platform availability before loading configuration. Windows Server configuration is validated through the same opened non-reparse handle that is read, with trusted owner and write-restricted DACL checks (§16).
- Keys: Server `max_file_channels` (§12), `max_file_size` and `file_timeout` (§13), `listen`, `log_level`, `identity_key` (Server key file, default `/etc/stpt/server_key` on Unix or PROGRAMDATA/stpt/server_key on Windows), `authorized_keys` (directory, default `/etc/stpt/authorized_keys` on Unix or PROGRAMDATA/stpt/authorized_keys on Windows), `exit_grace` (seconds 0–60, fractions allowed, default 1; §10). The Client also accepts `max_file_size` and `file_timeout` (§13). The Client's default user key is `id_ed25519` in its configuration directory.

# 5	Errors and logging
- A role returns `Result<ExitCode, error::Error>`. `main` prints an error once as `stpt: <error>` on standard error and exits with `Error::exit_code` (now always 255). Command line errors are clap's (exit 2). Lower modules have their own error types (`config::Error`, `quic::Error`, `identity::KeyFileError`, `trust::Error`), converted with `From`. Errors of the Server key check are multi-line (§7). A protocol failure found by the Client (`wire::Failure`: code and local reason) is `Error::Protocol`, printed as `stpt: protocol: <reason> (<CODE>)`; a close by the Server is a transport error printed with the code name (`stpt: transport: closed by the peer: VERSION_NEGOTIATION_FAILED`).
- The final error is printed directly, not as a log event: it is also shown when the configuration fails, before logging starts, and under `-q`.
- Log events: `tracing` with a `tracing-subscriber` fmt subscriber on standard error, installed once after the configuration is read; no ANSI colours, no log files (under systemd standard error goes to the journal, RK001).
- Level: `-q` error; `-v` info, `-vv` debug, `-vvv` trace; else the Server's `log_level`; else Client warn, Server info.
- Format: Client `LEVEL message fields`; Server adds UTC time and module (`2026-10-14T10:40:00Z DEBUG stpt::server: listen address listen=[::]:843`).
- Peer input in the log: only as `?` fields (Debug escaping of line breaks and control characters), so a peer cannot forge lines or inject terminal sequences; `%` (Display) only for values the program produced or the local user gave. Secrets are never logged.

# 6	Transport
PROTOCOL.md §6–§8.2, §13.3. `quinn` (QUIC) over `rustls` (TLS 1.3) with the `aws-lc-rs` crypto provider.

- Async: one multi-threaded `tokio` runtime per process (`quic::runtime`), created by the role; Connections and PTY masters (§10) run on it, the rest of the program is synchronous.
- Sockets: created with `socket2`. `[::]` is set dual-stack explicitly (`IPV6_V6ONLY` off), so it does not depend on the system default (Linux `net.ipv6.bindv6only`, Windows on by default); a specific address listens on that address only. The Client binds the unspecified address of the Server's family, port 0.
- QUIC: version 1 only (`EndpointConfig::supported_versions`). Transport parameters: no unidirectional streams; bidirectional stream limit for the peer 1 on the Server (the control stream), 0 on the Client, raised only after authentication (RB006); no datagrams; idle timeout 60 s; Client keep-alive PING after 15 s idle; Server migration on.
- TLS (`tls`): provider reduced to TLS 1.3 with AES-128-GCM, ChaCha20-Poly1305, AES-256-GCM and the groups X25519MLKEM768, X25519 (this order); ALPN `stpt` only, a Client offering no or another ALPN fails the handshake; no client certificates, no 0-RTT, no session resumption (no tickets, no session cache on either side). SNI: a DNS name is sent, an IP address is not (rustls `ServerName`).
- Hybrid group: rustls selects the first group in the Client's `supported_groups` that the Server supports. The Server cert resolver (`ServerIdentity`) therefore aborts the handshake when the Client lists X25519 before X25519MLKEM768, so X25519 is negotiated only with Clients without the hybrid group (PROTOCOL.md §6.2).
- Server key: Ed25519 Raw Public Key (RFC 7250) of the Server Identity (§7).
- Client verification (`tls::ServerKeyCheck`, a rustls `ServerCertVerifier`): only Raw Public Keys, signature scheme Ed25519 only, the handshake signature verified with the presented key. The verifier decides on the presented SubjectPublicKeyInfo with the stored key and the `--fingerprint` (`Expected`) and records the key with its `Verdict`: `Trusted` lets the handshake go on; `Unknown`, `Changed`, `Mismatch` abort it, and the Client reads the verdict to report the reason (§7).
- Client Endpoint: `quic::client` binds once per command; `quic::connect` may run on it several times (reconnect after a confirmation, §7). A regular close sends NO_ERROR (`quic::NO_ERROR`) and waits until the Endpoint is idle, so the Server sees the close.
- Server Connection lifecycle: accept, TLS handshake (failures logged with their reason, info), HELLO (§8), then wait for user authentication until its deadline; log the close with the remote address and either the Client's close reason or the Server's code and exact reason. Shutdown: TERM (systemd stopping the service) or INT (Ctrl+C in the foreground), handled from before `listening` on, closes every Connection with SERVER_SHUTDOWN and waits at most 3 s until the Endpoint is idle, then the Server exits with 0; the Sessions end with the process (PTYs closed: SIGHUP). The Client reports `transport: closed by the peer: SERVER_SHUTDOWN`.
- `rustls` is built without its `logging` feature and `quinn` without `log`, so no `log` bridge is needed; handshake errors reach the log through the `quinn` error values.
- Close reasons: `stpt` closes with an empty reason phrase (`quic::NO_ERROR`, `b""`). After a failed TLS handshake `quinn` itself sends the `rustls` error text in the transport close (e.g. `invalid peer certificate: UnknownIssuer`); quinn has no option to suppress it, and PROTOCOL.md §13.1 allows it. A received reason phrase is never acted on; it is shown only escaped (`quic::Error` writes it with Debug escaping, as quinn's own Display writes it unchanged), so a peer cannot put line breaks or terminal control sequences into the Client's error message.

# 7	Server Identity and trust store
PROTOCOL.md §9.

- Server key file (`identity`): Ed25519 private key, PEM PKCS#8 (`-----BEGIN PRIVATE KEY-----`, as `openssl genpkey -algorithm ed25519` writes it, so an administrator can also supply one). Default `/etc/stpt/server_key`, setting `identity_key`.
- Created at the first start if missing: parent directory created, file opened with `create_new` and mode 0600 (never replaces a file; if another process created it meanwhile, that file is read), key generated by `aws-lc-rs`, written and synced. The Server logs `Server key created` with path and fingerprint; at every start it logs `Server key` with path and fingerprint.
- Loading: on Unix the open file must not be accessible by group or others (`permissions 644 are too open … (chmod 600)`), checked on the open handle; the key must be PKCS#8 Ed25519 (another algorithm or a damaged file is an error naming the file). Errors end the Server before it binds its socket.
- `stpt server --fingerprint` loads or creates the key, prints the fingerprint on standard output and exits; it needs the same rights as the Server.
- Fingerprint (`identity::Fingerprint`): SHA-256 over the SubjectPublicKeyInfo, text `SHA256:` + base64 without padding. Parsing accepts only the full form (no prefix, no padding, no other case), so a shortened fingerprint is refused by the command line.
- Trust store (`trust`): file `known_servers` in the Client configuration directory (`~/.config/stpt/`, `%APPDATA%\stpt\`). One entry per line, `HOST:PORT KEY`, KEY = base64 of the SubjectPublicKeyInfo (with padding); empty lines and `#` comments are kept. A syntax error or two different keys for one address is an error naming file and line (fail closed); the same entry twice is accepted. Changes rewrite the whole file into a temporary file and rename it over the old one. A new file starts with a comment explaining the format and `stpt trust remove`.
- Client connect (`client::connect`), with the stored key and `--fingerprint`:
  - Stored key or fingerprint known: the presented key must equal the stored key and match the fingerprint, whichever is given. A key verified by `--fingerprint` for an address without entry is stored.
  - First contact (neither): the handshake is aborted, the Client shows the fingerprint and asks; only `yes` (any case) confirms. After a confirmation the key is stored and the Client connects again expecting exactly that key. No Server deadline (CLIENT_HELLO 10 s, RB004) runs while the user reads the fingerprint, and the second handshake proves that the Server holds the key.
  - Asking needs a terminal on standard input and standard error; otherwise the Client ends with the fingerprint and the advice to use `--fingerprint`.
  - Changed key or fingerprint mismatch: the Client ends with both fingerprints in full; for a changed key it names `stpt trust remove HOST:PORT`, which is the only way to replace an entry (no prompt offers to accept the new key).
- The host is resolved with the system resolver; only the first address is used for now.
- Not yet: key rotation (PI003/RI004), hashing of host names in the trust store, system-wide trust store.

# 8	Messages and HELLO
PROTOCOL.md §7, §8.1, §10, §11, §13.

- CBOR (`cbor`): own codec of the subset STPT uses (`Value`: unsigned and negative integers, byte and text strings, arrays, maps, booleans, null). The encoder writes deterministic encoding: shortest arguments, definite lengths, map keys sorted bytewise by their encoding. The decoder accepts only that: it rejects indefinite lengths, tags, floats, other simple values, reserved additional information, arguments longer than needed, map keys out of order or duplicate, invalid UTF-8, nesting deeper than 16 (the message array is depth 1) and bytes after the item. A claimed array, map or string length larger than the remaining input is refused before any allocation.
- Frames (`wire`): QUIC varint length (any valid form accepted, shortest written), then one CBOR item. A frame of length 0 is a protocol violation; a length over the receiver limit (65535, the minimum and default of §13.4; `stpt` announces no larger one) is refused with LIMIT_EXCEEDED before the payload is read. The end of a stream inside a frame is a protocol violation. `Message` is `[type, {* int => any}]`; unknown body keys are kept and never asked for.
- `wire::Failure` (error code and reason) is a locally found reason to close; the peer gets only the code with an empty reason phrase (PROTOCOL.md §13.1), the reason goes to the Server log or the Client's error message. `wire::Code` holds the codes of §13.2 and their names.
- HELLO (`hello`): wire version 0xFF000001 only. The Client offers it plus one random GREASE version (0x?A?A?A?A, repeated digit) and one random GREASE capability with parameter null; terminal commands offer no service capabilities. The internal file Client API can offer capability 1; the Server selects a valid profile-1 offer with its maximum capped by `max_file_channels` (default 8, 0 disables selection). Malformed or unsupported offers are ignored, and invalid selections fail closed. Limits are sent only when they differ from the default. The Server selects the highest common final version, else the highest common draft version, never GREASE; none: VERSION_NEGOTIATION_FAILED. SERVER_HELLO lists method 1 (`publickey-ed25519`).
- Validation: CLIENT_HELLO needs a non-empty list of uint versions; capabilities a map with uint ids; limits a map with integer keys and a message size of at least 65535. The Client checks SERVER_HELLO: a version it offered and not GREASE, only capabilities it offered and not GREASE, a non-empty list of methods. Every violation is PROTOCOL_VIOLATION.
- Server sequence (`server::serve_connection`): accept the control stream and read CLIENT_HELLO within 10 s (TIMEOUT); the first message must be CLIENT_HELLO; answer SERVER_HELLO; Established; then user authentication (§9) and the Authenticated control stream (below). The end or a reset of the control stream is PROTOCOL_VIOLATION at any time. Deadlines are `server::Deadlines` (shorter in tests). An internal `End` (Connection lost, or a `Failure` the Server closes with) lets every step use `?`.
- Client sequence (`client::Connection::hello`): open the control stream, send CLIENT_HELLO, read SERVER_HELLO within 10 s (TIMEOUT, PROTOCOL.md §13.3), check it, including that method 1 is offered. The Client keeps both directions of the control stream until it closes the Connection: dropping a quinn stream sends FIN, which the Server would treat as a violation. A failed step (`Connection::failed`) closes with the code of the failure.
- Permitted messages (`control::check`, PROTOCOL.md §3.1, §8.1, §11.4): one table of the control messages, their sender and the Connection state they belong to: CLIENT_HELLO and SERVER_HELLO in Handshaking, AUTH_REQUEST and AUTH_RESULT in Established, the requests (SESSION_TERMINATE, SESSION_DETACH, SESSION_LIST) and REQUEST_RESULT in Authenticated. Every message read from the control stream is checked against it, by the Server with sender Client and by the Client with sender Server. A message out of state or direction, a Channel message (CHANNEL_OPEN, TERMINAL_*) on the control stream, or an unknown type is PROTOCOL_VIOLATION.
- Requests (§8.4): on the Authenticated control stream the Server reads requests in a loop; each needs a uint request ID (key 0) and a valid body, else PROTOCOL_VIOLATION. Each runs in its own task, so a long one (termination) holds up no other; one writer task sends the results in the order they are ready. A request ID still without a result is a violation; over 16 outstanding requests the result is LIMIT_EXCEEDED. The Client sends one request at a time and waits up to 60 s for its result (a termination takes the Server's grace period).
- Channels (§8.3): after authentication the Server accepts streams and reads each one's first message (limit 65535). CHANNEL_OPEN of kind 1: terminal Channel (§10); kind 2 requires the negotiated file capability and dispatches to `files` (§12), otherwise PROTOCOL_VIOLATION. Another kind is rejected with CHANNEL_REJECTED (RESET_STREAM and STOP_SENDING), and the Connection stays. Another first message, an invalid one, or FIN before CHANNEL_OPEN closes the Connection with PROTOCOL_VIOLATION; a stream reset before CHANNEL_OPEN is ignored. Each stream is handled in its own task; the stream limit (10) bounds them.
- Priority: both sides set send priority 1 on the control stream (`control::CONTROL_PRIORITY`); terminal streams keep 0 and file streams use -1, so control and interactive data take priority over file traffic (§8.1, §16.3).

# 9	User authentication
PROTOCOL.md §12, §13.3, §13.4.

- User key (`auth::UserKey`): Ed25519, PEM PKCS#8 as `openssl genpkey -algorithm ed25519` writes it (v1 and v2 accepted), read by `identity::read_private_key` with the same Unix owner-only or Windows private-DACL check as the Server key. Default `id_ed25519` in the Client configuration directory, `-i/--identity PATH` for another file. It is loaded before the Client connects; a missing file ends with the openssl command that creates it (`&& chmod 600` on Unix). `stpt keygen` comes with RI001.
- AUTH_REQUEST (`auth`): method 1, Account (at most 256 bytes, else LIMIT_EXCEEDED), raw 32-byte key, 64-byte signature over the deterministic CBOR of `["STPT user authentication", exporter, method, Account, key]`. The exporter value is the TLS exporter of the Connection (`quinn::Connection::export_keying_material`, label `EXPORTER-STPT-user-auth`, empty context, 32 bytes); each side computes it itself. Verification: `aws-lc-rs` Ed25519 (RFC 8032).
- Authorized keys (`authorized`): directory `authorized_keys` (default `/etc/stpt/authorized_keys` on Unix or PROGRAMDATA/stpt/authorized_keys on Windows), one file per Account named like the Account, kept by the administrator. Line: base64 of the key's SubjectPublicKeyInfo (second line of `openssl pkey -pubout`), optional label of 1–64 bytes; `#` comments. Directory and file must be owned by root or by the Server's own user and not writable by group or others, the file must be a regular file; otherwise, or with an invalid line, the file is ignored (fail closed) and the reason logged. An Account name that is not a plain file name (`/`, `\`, `.`, `..`, control characters) is treated as an unknown Account.
- Accounts: `authorized::SystemAccounts` asks the system user database (`getpwnam` through `nix`); tests use their own `Accounts`.
- Decision (`Authorizer::decide`, in `spawn_blocking`, as `getpwnam` and file reading block): signature verification, Account lookup and reading the keys file all run, whichever fails; the decision is made once after them. The exact reason (invalid signature, no such Account, keys file missing, unsafe or invalid, key not listed) goes to the Server log with Account (Debug-escaped) and key fingerprint; the Client gets AUTH_RESULT false.
- Server sequence (`server::authenticate`): AUTH_REQUEST after AUTH_REQUEST until the authentication deadline (60 s); another message type before authentication, or an unoffered method, is PROTOCOL_VIOLATION. A failure is answered no earlier than 300 ms (`Deadlines::failure_delay`) after its AUTH_REQUEST, so the response time does not depend on the reason; the 6th failure closes with AUTH_FAILED instead of a result.
- Authenticated Connection: the Server logs Account, key fingerprint and label and raises the bidirectional stream limit to 1 + 10 (§8.2, §14.5); Channels and requests then follow §8. A further AUTH_REQUEST or CLIENT_HELLO is PROTOCOL_VIOLATION.
- Client (`client::Connection::authenticate`): one key, one AUTH_REQUEST, AUTH_RESULT within 10 s (TIMEOUT). Refused: the Client closes regularly and ends with the key fingerprint and its authorized keys line for the administrator.

# 10	Terminals
PROTOCOL.md §14, §15.1, §15.4, §15.5.

- PTY (`pty`, Unix only): `Pty::open` opens a master/slave pair (`openpty`) with the window size of the Channel (`terminal::Size`: columns, rows, pixel sizes). Termios: system defaults plus `IUTF8` on Linux (and Apple systems); no modes come from the Client. Both descriptors are close-on-exec.
- Master: non-blocking, registered with the Tokio reactor (`AsyncFd`), so reading output and writing input wait without a thread per terminal. `read` returning 0 means end of output: no process holds the slave any more (Linux reports EIO). `resize` sets the size with `TIOCSWINSZ`; the kernel sends SIGWINCH to the foreground process group.
- Processes (`process`, Unix only): `Account::lookup` reads the Account from the user database (`getpwnam`, groups with `getgrouplist`; an empty shell means `/bin/sh`). `spawn` starts the Session's program with `tokio::process` (exit status awaited without a thread):
  - always through the Account's shell, so `nologin` or `git-shell` keep their effect: login shell with argument 0 `-NAME` (as login and sshd), a command line with `-c`, an argument vector with `-c` and each element in single quotes (`'` as `'\''`), so it is neither split nor expanded;
  - on the PTY slave (standard input, output and error, controlling terminal) or with three pipes;
  - in the child before exec (`pre_exec`, system calls only, nothing allocated): every signal back to its default disposition (signals the Server ignores, e.g. INT and QUIT when a shell started it in the background, would stay ignored across exec, and a shell cannot even trap them), `setsid`, so the program has its own session and process group; with a PTY the slave becomes the controlling terminal (`TIOCSCTTY`); then `setgroups`, `setgid`, `setuid` when the Server runs as root; a Server not running as root can start processes only for its own Account; working directory the home, else `/` with a notice on the terminal;
  - environment built from scratch, nothing of the Server's environment; later entries win: `HOME`, `USER`, `LOGNAME`, `SHELL`, `PATH` (Debian `login.defs` values, root gets the `sbin` directories); the system login environment, read at every Session start from `/etc/environment`, `/etc/locale.conf` and `/etc/default/locale` as pam_env reads them for sshd (`KEY=VALUE`, `#` comments, optional `export ` and quotes, no expansion; missing files skipped), so PATH and the system locale are those of an ssh login; the variables the Client sent that passed the allowlist (its locale wins over the system's, as with AcceptEnv); `TERM` (with a PTY only) and `STPT_SESSION`. `HOME`, `USER`, `LOGNAME`, `SHELL`, `TERM` and `STPT_SESSION` are never taken from the files;
  - signals (`signal_group`, §14.9) carry the permissions of the Account, never those of the Server: as root a child is forked that takes the Account's groups, group and user and calls `kill` on the process group, then `_exit`s with the errno (system calls only, no exec, nothing allocated after the fork); the Server waits for it in a blocking task. So a signal never reaches a process the Account could not signal itself, e.g. one started with sudo. A Server not running as root runs as the Account and calls `kill` itself;
  - not done (unlike sshd with PAM): PAM sessions and limits, environment from other PAM modules, utmp/wtmp/lastlog, systemd-logind sessions.
- Messages (`terminal`): `Open` is the terminal CHANNEL_OPEN with every parameter of §14.6, encoded by the Client and validated by the Server (a malformed parameter: CHANNEL_REJECTED; environment limits: LIMIT_EXCEEDED; attach parameters on create and creation parameters on attach: CHANNEL_REJECTED). Session ID: 16 bytes from the system random generator, text form 32 hexadecimal digits.
- Server side of a Channel (`attachment`): a CHANNEL_OPEN without a Session ID creates a Session (§11) and attaches with the replay from offset 0; with one it attaches to that Session of the Account. Then TERMINAL_ATTACHED, the replay, the exit status if the Session has exited, and two concurrent loops:
  - input: TERMINAL_DATA to the PTY or to standard input (dropped once the program closed its input); TERMINAL_EOF closes standard input (without a PTY only; from any Attachment); a read-only Attachment sending input is a violation; TERMINAL_RESIZE sets the PTY size (`TIOCSWINSZ`, so the foreground process group gets SIGWINCH) between the input before and after it; TERMINAL_SIGNAL (ids 1–7; a report-only or unknown id is a violation) goes, with a PTY, to the foreground process group of the PTY (`tcgetpgrp` on the master), without a PTY to the process group of the command, also after TERMINAL_EOF; a target that is gone ignores it; another type, EOF with a PTY, data after EOF, resize without a PTY or an invalid message close the Connection with PROTOCOL_VIOLATION;
  - output: the Session's events (output pieces, finally the exit status) as TERMINAL_DATA, TERMINAL_STDERR and TERMINAL_EXIT, then FIN; later Client messages are discarded until its FIN, which confirms the exit status. A detach by the Server (takeover, detach request) ends with FIN, a stall with RESET_STREAM TIMEOUT.
  - The Client's FIN, a reset or a lost Connection end only the Attachment; the Session keeps running (§14.10, §3.4).
  - A Connection may have one Channel per Session; a second is rejected with CHANNEL_REJECTED.
- Client (`client::Connection::terminal`): `connect` opens a Channel with a PTY running the login shell: TERM from the environment if valid, else `xterm-256color`; size of the local terminal, else 80×24; `--name` passed on. `connect --attach SESSION` attaches (with `--takeover`, `--read-only`), with a PTY if the Session has one (from the list). `exec` opens one without a PTY: the arguments joined with spaces into one command line, as ssh does; `--no-shell` sends them as an argument vector. Both pass `LANG` and `LC_*` only. Rejection or reset of the Channel ends the Client with the code name (`terminal: rejected by the Server: SESSION_NOT_FOUND`).
  - Input: a thread reads standard input and hands it to a task that sends TERMINAL_DATA; at the end of input TERMINAL_EOF without a PTY, nothing with one (Ctrl-D is in-band). With a PTY the escape of ssh applies: after a line end `~.` detaches (FIN, exit 0, `detached; Session ID keeps running`), `~~` sends one `~`. The escape follows escape sequences in the input: what the terminal emulator sends on its own (mouse and focus reports, answers to queries: `CSI` with private parameters, `CSI I`/`CSI O`, X10 mouse, OSC) does not end the line start, keypad Enter (`ESC O M`, sent in application keypad mode) is a line end, other sequences (arrows, function keys, Alt) and the Esc key are typing. A read holds whole keys, so an ESC alone at the end of a read is the Esc key. At `-vvv` the Client logs the shape of each read (printable characters masked, escape sequences shown) to diagnose the escape. After TERMINAL_EXIT the task sends FIN and waits until the Server acknowledged it (`SendStream::stopped`), as closing the Connection would drop it and the exit status would stay unconfirmed.
  - Read-only (`--read-only`): nothing is sent, not even the window size or what the terminal emulator reports on its own (focus, answers to queries); with a PTY `~.` still detaches, without one Ctrl+C detaches.
  - Terminal modes: the Client writes the modes of TERMINAL_ATTACHED before the replay and follows the modes in the output (`modes`); when the Channel ends it returns them to their defaults (leaving the alternate screen first), and after an early end it also resets the colours and starts a new line, so the prompt appears below.
  - Window size (with a PTY and a terminal on standard output): a task sends TERMINAL_RESIZE when the size of the local window differs from the last one sent, so a burst of changes gives one message with the latest size. Unix: on SIGWINCH (`tokio::signal`). Windows: a poll every 250 ms, as a console read with ReadConsoleW reports no size changes.
  - Output: TERMINAL_DATA to standard output, TERMINAL_STDERR (without a PTY only) to standard error, unbuffered; any other message is a violation.
  - Ctrl+C without a PTY (`exec`): sends TERMINAL_SIGNAL INT (`tokio::signal::ctrl_c`, also a Windows console control event); the third press ends the Client with `interrupted` (255), for a command that ignores INT. With a PTY Ctrl+C is an input byte in raw mode.
  - Ending early: from the moment the Channel is opened, the Client handles the events that would end it at once (`console::termination`): Unix HUP (the terminal window was closed) and TERM; Windows closing the console, logoff, shutdown and Ctrl+Break (Windows allows 5 s after a close event). It then restores the local terminal, ends its direction of the Channel (FIN: detach) and closes the Connection with NO_ERROR, so the Server learns at once instead of after the idle timeout; exit 255, `terminated by HUP`. The Connection is closed regularly after every terminal Channel, also after errors. Final messages are written with errors ignored, as standard error may be gone with the window.
  - Exit code: the remote exit code, 255 if it does not fit into 8 bits; after a signal 255 and `stpt: the remote program was killed by signal NAME`, as ssh. A Channel ended by the Server without TERMINAL_EXIT: 0, `detached by the Server`. A lost Connection: with a PTY automatic reattach first (§11); then 255 and the `stpt connect --attach ID` that continues, except after SERVER_SHUTDOWN, which ends the Sessions.
- Local terminal (`console`): with a PTY and a terminal on standard input, raw mode while the Channel runs (Unix: `cfmakeraw`; Windows: line input, echo and processed input off, virtual terminal input on), restored when it ends, also on errors. Window size: `TIOCGWINSZ` on standard output; Windows: the visible window of the console screen buffer. Windows output: written with WriteFile in the UTF-8 code page with virtual terminal processing (and DISABLE_NEWLINE_AUTO_RETURN with a PTY), as the standard library's console writer rejects bytes that are not UTF-8; console input: ReadConsoleW converted to UTF-8, as the standard library would end input at Ctrl+Z.

# 11	Sessions
PROTOCOL.md §3.2, §15.

- Store (`session::Store`, both Server platforms): all Sessions of the Server in a map ordered by ID, shared by all Connections; a Session is found only with the Account that owns it, so a foreign ID is handled as an unknown one (§15.2). Sessions do not survive a Server restart.
- Creation: Account lookup and system environment (blocking task), then under the store lock: at most 64 Sessions per Account (LIMIT_EXCEEDED), unique name among them (SESSION_NAME_IN_USE), program start; a failed start rejects the Channel with CHANNEL_REJECTED. Session ID: 16 random bytes; `STPT_SESSION` holds it.
- Output: one task per Session reads the PTY or the pipes (16 KiB per read), numbers each piece into the output buffer (`buffer`, 256 KiB, offsets from 0) and hands it to every Attachment through a queue of 8 pieces, at the pace of the slowest; an Attachment whose queue stays full for 10 s (stall limit) is ended with TIMEOUT. Without Attachments output goes to the buffer only, so the processes never block. After the program exited, output is sent until its end, at most for the grace period (`exit_grace`, default 1 s), so a background process holding the PTY does not hold the exit.
- Attach (`Session::attach`): under the Session lock, so live output follows the replay without gap or overlap: state Running or Exited (else SESSION_NOT_FOUND), takeover ends the other Attachments, at most 8 Attachments (LIMIT_EXCEEDED), replay from the buffer. Fresh attach: from the start of the current screen (after the last alternate-screen switch, offset 0 if none) if it lies in the last 16 KiB, else the last 16 KiB from their first line feed; resume: from the offset, or from the start of the buffer if older (an offset beyond the end: CHANNEL_REJECTED). After a fresh or lossy attach to a PTY the Session redraws: the PTY is one row smaller for 100 ms, so the foreground group gets SIGWINCH twice with a real size change (ncurses programs repaint fully only then); the size is restored unless an Attachment set another meanwhile. TERMINAL_ATTACHED carries the sequence that sets the terminal modes (`modes`): the Session follows, in PTY output, the switches of 14 DEC private modes (cursor keys, mouse, cursor visibility, alternate screen, focus, bracketed paste) and the keypad mode, nothing else. Attachment IDs count from 1 per Session.
- Size: the PTY has the size of the active Attachment, the one that attached, typed or resized last (read-only ones never); each Attachment's last size is kept.
- States: Running → Exited when the program exits; Exited → Terminated when an Attachment's Client confirms the exit status with its FIN after TERMINAL_EXIT, or by removal; Running → Terminating → Terminated by termination. A Terminated Session leaves the store; with its last reference the PTY is closed.
- Retention Policy (a task checks every second): a Session without Attachment is terminated when the detach timeout of its Client runs out (key 6 of CHANNEL_OPEN, capped at 100 years so that deadlines stay within the range of the clocks; 0: as soon as it has none); an Exited Session without Attachment is removed 24 h after the exit. No other limit for detached Running Sessions.
- Termination (`Session::terminate`, §15.6): with a PTY HUP to every process group of its terminal session (found in /proc: processes whose session ID is the program's), without a PTY TERM to its process group, both with the Account's permissions; KILL after the grace period (5 s) or at once with force; done when the program has exited, or 1 s after KILL even if processes are left (uninterruptible wait). An Exited Session is removed at once. The Attachments get the exit status (or a detach, if already Exited).
- Requests (`requests`): SESSION_LIST pages in ID order as many Sessions as fit the Client's message size limit (`more` if others follow); key 1 gives one Session or SESSION_NOT_FOUND. Entries: name, state, Unix times, the creating key and its label, PTY, command for display (256 bytes), exit status, removal time, Attachments with key, label, read-only, active and the current remote address of their Connection (IPv4-mapped addresses as IPv4). SESSION_TERMINATE answers when the Session is Terminated; SESSION_DETACH ends one Attachment (or ATTACHMENT_NOT_FOUND) or all.
- Client (`commands`): `sessions` prints the list (all pages) as a table: ID (first 12 digits), name, state, age, number of Attachments, command. `terminate` and `detach` resolve the Session and send the request; an error code ends the Client with its name.
- Not yet: Server settings for the limits above (only `exit_grace`).
- Migration (`client::follow_network`, §15.12 of the protocol), while a terminal Channel runs, with and without a PTY: every second `quic::route_source` asks the system for the source address towards the Server (a connected UDP socket; nothing is sent, works the same on Linux and Windows, no dependency for network events). On a change `quic::rebind` moves the Endpoint to a new socket: new connection ID, PING at once. Without it the wildcard socket would use the new address only with the next packet, at an idle Client the keep-alive after up to 15 s, and with the old connection ID. Without a route it waits. The Server allows migration (`migration(true)`) and logs and lists the current address. `tests/network_change.sh` changes the address for real in network namespaces (root).
- Automatic reattach (`client::terminal`, §15.12 of the protocol): with a PTY only, as input has no offsets and a pipe into `exec` would silently lose data. What outlives the Connection is local: raw mode, the stdin reader and escape state (`LocalInput`), followed modes, output offset, the termination signals (`Terminal`). A Connection that ended by `TimedOut` or `Reset` starts attempts, each a full login with the same trust checks (an unknown key is an error, nobody is asked) and an attach with resume; 20 s per attempt, pauses of 0, 1, 2, 4… up to 30 s, for `reattach_timeout` (default 1 h, 0: off). A close by the Server does not reattach. Key changed, key refused, Session gone or a protocol violation end it at once. After attaching, SESSION_DETACH ends the old Attachment, without waiting for the result: attaching first keeps a Session with a short detach timeout alive. Input during the outage is dropped except for the escape; `Enter ~ .` gives up. Without lost output key 3 of TERMINAL_ATTACHED is ignored, as the terminal still has its modes; with lost output the modes are reset and set from key 3. With an alternate screen active the messages go to the last row without moving the cursor (a line feed would scroll the screen behind the program's back), and after a resume without loss the Client sends TERMINAL_RESIZE with one row less and, 200 ms later, the real size, so the program repaints; not when read-only.

# 12	File Channel envelope
PROTOCOL.md §16.2–§16.4; RE001. Ordinary file operations using this Channel are described in §13.

- Negotiation (`hello`, `files`): capability 1, profile 1, maximum file Channels at least 1. The Server narrows to its configured per-Connection cap (default 8); 0 disables selection. The Client validates the profile and maximum against its offer. Existing terminal commands keep their capability-free offer plus GREASE, so old terminal-only peers remain compatible. Wire version stays 0xFF000001.
- Access boundary: the dispatcher is installed only after authentication. A kind-2 opening without the selected capability closes the Connection. An accepted Channel sends FILES_READY (0x4000), has one bidirectional stream and creates no Session or Attachment. No Client or Server filesystem access is performed by the envelope.
- Admission: one shared semaphore per Connection on each Endpoint; a Client slot is reserved before opening the stream, a Server slot before FILES_READY. Overflow resets only that Channel with LIMIT_EXCEEDED. The same 10-Channel QUIC budget is shared with terminals; negotiation reserves no transport stream credit. File streams use send priority -1, below terminal 0 and control 1.
- Client API (`Connection::open_files`, `files::Channel`): requires successful authentication and selected capability, sends CHANNEL_OPEN and validates FILES_READY. Stream-credit and opening waits are bounded (10 s each); an opening timeout resets both directions with TIMEOUT, preserving the Connection. Dropping a Channel or cancelling its opening aborts both directions and releases the local slot. The `fs` commands use this API; terminal commands keep their previous negotiation.
- Idle lifecycle: Client FIN is answered with Server FIN; `Channel::close` waits for Server FIN and acknowledgement of its own FIN; `Channel::wait_closed` watches an idle Channel for Server FIN and answers it with Client FIN. Slots are retained until both directions end or are aborted. The Server also watches STOP_SENDING while idle, so a half-cancelled Channel cannot hold a slot indefinitely. Connection loss releases its file resources. Neither FIN nor FILES_READY is a file-operation success acknowledgement.
- Dispatch: FILE_REQUEST starts an Account-owned worker on Unix (§13) or Windows (§17). Other idle messages, including repeated CHANNEL_OPEN/FILES_READY and unknown types, are protocol violations. The parent validates phases concurrently with bulk output, so premature receipts and pipelined requests cannot be hidden in a pipe until the worker reaches another phase.
- Validation: unit tests cover negotiation and configuration; loopback QUIC tests exercise authenticated dispatch, stream rejection, opening timeout, local/remote limits, FIN, cancellation, Connection loss and control-stream independence. A Unix test keeps a terminal Session running after closing its concurrent file Channel. Run `cargo test` and `cargo clippy --all-targets -- -D warnings` on both primary platforms.

RE001 validation (2026-11-21, version 0.3.3-0): `cargo test` passed on Windows (160 tests) and Debian 12 in Docker (223 tests, 6 existing ignored tests). `cargo clippy --all-targets -- -D warnings` passed on both platforms; `cargo fmt --check` and `git diff --check` passed. Linux tests used Rust 1.99.1 and procps for the existing process-group test. The ignored tests are two privileged process tests and four long Connection-loss tests.

# 13	File operations and transfers
PROTOCOL.md §16.5–§16.13; RE002. The mandatory POSIX path and kind/size representations of §16.18–§16.19 are used as the base grammar; expanded path/metadata handling is described in §15, with native Windows file service described in §17.

- CLI (`cli`, `file_client`): `fs push ACCOUNT@HOST LOCAL REMOTE`, `pull ACCOUNT@HOST REMOTE LOCAL`, `stat`, `list`, `mkdir`, `remove`, `rename`. Remote paths are absolute POSIX or Windows drive paths (§15); the Unix Server accepts POSIX paths. There is no shell expansion, implicit parent creation, recursion or local-name derivation from a peer's listing. Local paths remain native. Every command reuses Server trust and user authentication, offers capability 1 with maximum 1 and uses operation ID 0 on its own file Channel. The Server supports sequential operations with strictly increasing IDs from 0 on reused Channels.
- Authority (`process::Account::file_worker`): the Server executes its own binary with private `__stpt-file-worker` arguments and two IPC pipes. The child receives exact Account supplementary groups/GID/UID before exec, an empty environment and `/` as working directory. On Linux, `/proc/self/exe` executes the loaded Server image even if its file was unlinked or replaced, and does not require the Account to traverse the installation directory ([proc_pid_exe(5)](https://man7.org/linux/man-pages/man5/proc_pid_exe.5.html)); other Unix targets use the executable path. No shell is invoked, and a disabled interactive shell does not disable file service. An unprivileged Server refuses an Account it cannot assume or inherited groups exceeding the Account's current groups. The network runtime never changes thread credentials. No STPT Session or Attachment is created.
- IPC (`file_protocol`, `files`): bounded, strict CBOR messages with a private u32 length prefix, at most 65535 bytes, over stdin/stdout only. This framing and the reserved local failure message never appear on the QUIC wire. Input and output are relayed concurrently with stream cancellation and progress monitoring. The parent enforces operation IDs/directions/phases; the worker independently validates requests and filesystem semantics. Wire FILE_RESULT statuses are separate from stream errors.
- Limits: global maximum 32 active workers, in addition to the existing negotiated per-Connection Channel and shared QUIC stream limits. Admission remains charged through blocked Account lookup and process reaping. Both roles limit logical file size (default 8 GiB, maximum 2^61 - 1) and no-progress waits (default 60 s). Buffers and queues are bounded; no file-sized allocation or directory snapshot is taken. Native Account quotas, permissions, ACLs and read-only checks always apply. Listing emits one bounded entry per batch. Keep-alives do not extend operation deadlines.
- Operations (`file_worker`, `file_storage_unix`): read/write/stat/list/mkdir/remove/rename. The shared worker owns transfer/hash/checkpoint state; native filesystem operations are behind the platform storage module. Windows behavior is in §17. POSIX path components preserve native bytes; root is accepted only for stat/list. Descriptor-relative mutations pin parent directories and never use privileged checks followed by access as root. Stat/remove/rename act on final entries. Reads refuse final symlinks and use nonblocking open plus a regular-file check, so FIFOs/devices are never read. Listing may follow a final directory symlink and pins the opened directory while inspecting entries. Kind/regular-file size, POSIX modification time and low-nine-bit mode metadata are returned (§15); no source timestamps, owners, ACLs or modes are applied to a destination.
- Integrity (`file_protocol::Hash`): BLAKE3 is required/default; SHA-256 uses the existing AWS-LC dependency when explicitly requested. FILE_ACCEPTED confirms exact algorithm and length. Data blocks default to 32 KiB, maximum 60 KiB. Counts and offsets use checked u64 arithmetic through the wire bound; both ends incrementally hash actual transferred bytes. Early source EOF is failure; appended bytes are excluded and in-place source changes do not promise a snapshot. End-count/digest mismatch is INTEGRITY_ERROR. Downloads require receipt and final result; uploads require final result after verification/publication.
- Upload publication: a fresh private directory/file on the destination filesystem is requested with modes 0700/0600 and checked for private mode bits. Setup, writing and cleanup all use Account credentials. Only a verified complete upload is closed and atomically published using Linux renameat2(RENAME_NOREPLACE). Existing destinations remain untouched on failure. Existing-target upload replacement returns UNSUPPORTED, including with `replace=true`: ordinary POSIX rename cannot atomically constrain the replaced entry to a regular file. There is no delete/create or copy/delete fallback. Rename itself can explicitly replace compatible native entries atomically. Unsupported no-replace platforms/filesystems are refused.
- Download publication (`Destination`, `file_storage::LocalPublication`): Unix ordinary downloads use private mode-0700 directories and mode-0600 files; publication uses held source/destination directory descriptors. Windows ordinary downloads use protected owner/SYSTEM/Administrators DACLs and retain a source-file guard denying write/delete sharing; link/rename uses the source handle and pinned target directory. Retained data uses non-followed native opens and the same pinned publication primitives. Buffered writes and the writing handle's relevant close errors are checked before receipt; the Client publishes only after verified END and final OK. Create-only hard links cannot overwrite a racing destination; explicit pull replacement uses native rename. Private staging cleanup has an owner even if its blocking creation task outlives cancellation. No checked temporary source is later reopened by pathname for publication. Unsupported native facilities are refused.
- Failure and shutdown: early receiver/storage failure aborts only the Channel rather than draining arbitrary remaining data. Completed end/receipt boundaries allow a nonzero final result and Channel reuse. Local deadlines abort with TIMEOUT; protocol violations close the Connection. Normal interruption closes worker pipes and permits cleanup before reaping. A stuck worker is killed after a bounded grace period, reaped asynchronously while still charged to admission, and incomplete private staging cleanup is logged. Server shutdown waits briefly for workers. Server-instance upload retention and private Client checkpoints are described in §14; there is no automatic retry or claim of exactly-once execution. A lost modifying result is reported as potentially unknown; loss during teardown after final OK does not turn a known completed operation into an unknown one.
- Validation (2026-11-21, 0.3.4-0, Rust 1.100.0): `cargo test` passed on Windows (169) and Ubuntu VM (253, 6 existing ignored); a separate root run of the file integration suite passed all 21 tests. An earlier Debian 12 Docker run passed 252 tests with the same 6 existing skips. Clippy all targets with `-D warnings`, formatting and diff checks passed. Real CLI tests cover binary/empty transfers, both hashes, management operations, collisions, native symlinks, size limits, worker startup after binary unlink and root Server → nobody Account isolation. Worker fault tests cover wrong digest/offset, interruption, early EOF, reuse and non-UTF-8 names. Client tests cover bad digest, racing local publication, TIMEOUT and excessive accepted length. An independent Windows Client ↔ Linux Server smoke test passed a 256-KiB BLAKE3 roundtrip, empty SHA-256 roundtrip and stat, with local SHA-256 comparison of the binary files.

# 14	Explicit file resume
PROTOCOL.md §16.14–§16.17; RE003; program 0.3.5-0. No wire version or mandatory profile change.

- Client opt-in: `fs push/pull --resume-state DIRECTORY`. Each invocation uses a new authenticated Channel with ID 0; repeats explicitly request the original upload token or nonempty download checkpoint. The directory's bounded CBOR record binds actual verified TLS Server Identity, Account, exact wire path, local absolute native path, algorithm and replacement policy. There is no implicit fresh transfer, automatic retry, hash fallback or durable receipt. Unknown modifying outcomes remain unknown after lost final results.
- Client state (`file_checkpoint`): Unix owner/mode 0700 directory and mode 0600 files; Unix existing state-file owner/private-mode checks precede writes. Windows creates directories/files atomically with an explicit current-user owner and protected owner/SYSTEM DACLs, then validates actual existing/opened objects through non-reparse handles ([Microsoft security descriptors](https://learn.microsoft.com/en-us/windows/win32/secauthz/security-descriptors)). An OS file lock serializes invocations and is released on process exit. Record replacement uses a bounded fresh record; a crash may leave an unrecognized temporary file, which is refused rather than treated as valid state. Only successfully written complete DATA blocks advance the checkpoint, after flushing local writes. Resume truncates unconfirmed tail bytes and rereads the prefix into both verification and full-file hash contexts. Download publication still requires verified END, receipt and final OK; saved data must support the chosen native publication operation at the final destination. Successful transfer/cancellation clears known state files while preserving the lock inode. Refused resume leaves its previous state available for inspection or an explicit repeat. A zero-offset download checkpoint requires an explicit fresh transfer.
- Download Server (`file_worker`): no saved record. Open source with current Account authority and require the original total length. Rehash the requested prefix through the same open descriptor as the suffix; mismatch returns RESUME_UNAVAILABLE before acceptance. Acceptance confirms the exact offset, including offset equal to total length; END always hashes the entire logical file.

# 23 TCP forwarding (RG001–RG004, 0.5.0-0)

Capability 4 selects local, remote and dynamic TCP modes with aggregate rule/flow maxima. A kind-4 stream owns a rule; kind-5 streams carry independent TCP connections with framed DATA and directional FIN. Rule IDs are their QUIC stream IDs, scoped to the authenticated Connection. Rules and flows survive migration but never Connection loss; Sessions and Attachments are not involved. The standalone `forward` CLI opens one rule per Connection and never reconnects automatically. It offers no Client file capability.

`forwarding::runtime::State` holds a Connection-local registry and semaphore reservations at Connection, Account and process scope. Rule entries have Pending/Active/Dead watch state. Remote callbacks arriving before READY wait on that exact entry without connecting the local target. Revocation removes the registry binding and invalidates the entry before releasing resources. Flow reservations and rule ownership remain held through flow teardown. Per-rule JoinSets contain accepted-socket tasks; receiver tasks independently observe invalidation and Connection closure. An unfinished opener stream guard resets/stops on cancellation, avoiding accidental clean FIN when an owning task is aborted.

Each TCP direction reads/writes one bounded chunk at a time; there is no unbounded user-space relay queue. Frames are at most the ordinary 65535-byte receiver limit, DATA at most 61440 bytes and local chunks 16384 bytes. Per-write/partial-frame progress deadlines apply while clean boundary reads remain idle without a service timer. QUIC STOP_SENDING is observed independently even during TCP read idle. EOF drains that direction before socket shutdown; reset, truncation and cancellation abort both socket halves. Setup/stream-credit/SOCKS deadlines are 10 s and blocked progress 60 s. Rules use no idle timer. Limits include opening, half-closed and cancelling sockets. Default Connection 8/64, Account 32/256 and global 256/2048 rule/flow caps apply in both directions; the native-operation cap is 64. Post-authentication QUIC credit includes forwarding maxima, while the original ten non-forwarding Channels retain a separate shared budget.

Server policy is opt-in per Account in `[forwarding.accounts.NAME]`. Mode flags, permitted numeric target/bind networks and ports, optional exact DNS names and optional remote ingress filters intersect authorization. Every resolved numeric candidate is checked before connecting directly to that number; no second lookup can replace it. DNS results are capped at 16 candidates. A remote port-0 listener is provisional until its actual port passes policy. Remote destinations remain Client-only configuration, never Server input. Policies are immutable after startup; restart revokes all Connections. Per-key restrictions beyond the current Authentication Context remain RI003 work.

Unix helpers execute the existing image via the same credential-drop command builder as file workers, with empty environment, `/` cwd, Account groups/GID/UID and no shell. A connected socket or listener is returned over an inherited private Unix datagram socket using SCM_RIGHTS and close-on-exec receipt. DNS uses a separate bounded helper under those credentials and absolute names. Only checked numeric destinations reach connect helpers. Cancellation kills/reaps outstanding helper children, retaining their admission slot until reaped. Account lookup occurs on a bounded blocking task; its slot survives cancellation until it actually completes. Enabling nix `socket`/`uio` features supplies descriptor passing; no new direct dependency was added. Once transferred, the parent relays on the already authorized socket and never retries bind/connect with Server authority. Windows revalidates the current canonical Account and uses its current process token; native sockets are direct. Client/native Windows DNS uses bounded blocking resolution with reservations retained through completion.

The Client terminates a restricted no-authentication SOCKS5 CONNECT handshake. It sends no SOCKS header or premature payload to the target and returns success only after CONNECTED, including the connector's actual local socket endpoint. Non-loopback listeners require local opt-in; exposed SOCKS requires an ingress allowlist. No GSSAPI, username/password, BIND, UDP, Unix sockets, scoped IPv6 or automatic IDNA conversion is implemented. Runtime tests and native evidence/remaining coverage limits are recorded in [RG_REVIEW.md](RG_REVIEW.md).
